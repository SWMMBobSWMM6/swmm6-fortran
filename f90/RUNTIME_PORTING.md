# Porting the C# runtime to Fortran (module cpp_runtime, f90/runtime)

The SWMM6 engine is translated C++ → C# (`cs/gen`, gated byte-identical to the C++ reference on 480 models) →
Fortran (`f90/gen`: `swmm6_engine.f90` with every type and interface, and 62 submodules with the bodies, by
`tools/cs2x/Cs2F90.cs`; read `tools/cs2x/F90.md` and the header of `tools/cs2x/F90Types.cs` for the design). The
engine does `use cpp_runtime` and calls a C++-standard-library emulation. The C# version of that library,
`cs/runtime/*.cs` (namespace `Cpp`, 3,800 lines), is the specification of behaviour. This file is the contract
for the Fortran version.

## What has to exist

- **`f90/cs2f90_runtime.txt`** (the manifest, generated by the translator) lists every runtime type, component,
  module variable and procedure the engine uses, with its exact Fortran declaration and the C# member it stands
  for. **Its header sets the conventions** (kinds, `cpp_object` and its bindings, `cpp_slot`, erasure with makers
  and copy modes, arrays, runtime structs, the pending exception `cpp_exc` and `[throws]`, delegates, string
  literals, field pointers, identity, `swmm6_engine_init`). Read it first, all of it.
- **`f90/runtime_parts.txt`** says which part implements each manifest entry (A core, B containers, C C
  runtime, D streams/fs/runner). A TYPE's bindings belong to its part.
- **`f90/runtime/stub/cpp_rt_{a,c,b,d}.f90`** are the four part modules as stubs: every type complete as the
  engine sees it, every procedure with an empty body. `f90/tools/split_stub.py f90/runtime/stub` makes them from
  the translator's one-module stub `f90/runtime/stub/cpp_runtime_stub.f90`. They compile, and the engine
  compiles against them (`gfortran -fsyntax-only`). Use them for the parts that are not yours.
- **`f90/runtime/cpp_runtime.f90`** (a copy of the stub folder's) is the module the engine uses; it only
  re-exports the four parts.

## Layout

- Part P writes **`f90/runtime/cpp_rt_<p>.f90`**, `module cpp_rt_<p>`, with the same name, type names and
  components as its stub (add private components, helper types and procedures freely). The specification part
  of a module may `use` only the parts before it in the order **a, c, b, d** (Fortran modules cannot depend on
  each other in a cycle): C uses A; B uses A and C; D uses A, C and B.
- A body that needs a later part goes in a **submodule**: declare the procedure in the module as a separate
  module procedure (`interface; module function f(...) ... end function; end interface`) and implement it in
  `f90/runtime/cpp_rt_<p>_<name>.f90`, `submodule (cpp_rt_<p>) <name>`, which may `use` any part's module.
  This is how A reaches C's exception class or printf, for example.
- Every procedure is `recursive` (the engine is compiled with `-frecursive`, and runtime code calls engine code
  through bindings and delegates).
- Compiler and flags: gfortran 13, `-O2 -fwrapv -ffp-contract=off -fno-fast-math -frecursive
  -ffree-line-length-none -fimplicit-none -fno-range-check` (F90.md). No other floating-point flags.
- The engine's math is the system libm (gfortran's intrinsics call glibc's exp, log, pow, sin, ...; C++ and C#
  call the same functions), so no glibm translation is needed. Check each `cpp_math_*` entry against the C#
  (`.NET`'s Math.Round, Truncate, CopySign, Cbrt... are not all libm calls).

  Write the Fortran counterpart of the checks for your part.

## The gate

`gate/gate.py NAME "ENGINE" --ids FILE -j 1 --timeout 900` runs an engine command (`ENGINE model.inp r.rpt r.out`,
from the model's folder) and compares with the C++ reference outputs in `gate/ref_outputs`;
`gate/cmp1.sh /abs/path/engine ID` does one model. The 8-model smoke list is
`/tmp/claude-0/-home-claude/9f3dde4c-f353-52c4-b476-e410dd8d4e21/scratchpad/smoke.ids`
(`9cc1e3f15ad4` is OWA_EXTRAN/extran1_rectangular.inp, a small first model).
