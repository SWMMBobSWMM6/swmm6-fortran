# C# to Fortran: how tools/cs2x/Cs2F90.cs should map the generated engine

The Fortran engine is the last and hardest of the six: the generated C# (cs/gen: 577 classes, 117 virtual or
abstract methods, 823 lambdas, 235 throws and 32 try statements, all of it byte-identical to SWMM6 on 480
models) uses classes, generics, exceptions and closures, and Fortran has only the first, in its own form. This
file records the design. The SWMM5 Fortran port (/home/claude/swmm5-ports/f90, translated from C, 480/480
against EPA; runtime crt_base/crt_format/crt_io, build flags in its build.sh) is the starting point for the C
runtime: glibc-exact printf, strtod, sscanf, files.

## Compiler and flags

gfortran 13, `-O2 -fwrapv -ffp-contract=off -fno-fast-math -frecursive -ffree-line-length-none -fimplicit-none
-fno-range-check` (the SWMM5 port's flags plus -frecursive). Fortran calls the system's libm for exp, log, pow,
sin, ..., as the C++ and C# do, so no glibm is needed.

## Program structure

- All engine types in one module (Fortran modules cannot depend on each other in a cycle, and the engine's
  classes do), with the procedures in submodules so the compiler sees manageable pieces.
- Every engine class extends a root type `cpp_object` (in the runtime) with overridable type-bound procedures
  `clone`, `assign`, `dispose` and whatever else the runtime must call on an arbitrary object (C#'s ICopy,
  IDisposable, IHashFn, IBinFn). An engine object is always held as `class(T), pointer`; C# reference identity
  is pointer association.
- Instance methods are type-bound procedures (`deferred`/overridable for C#'s virtual and abstract ones,
  `non_overridable` for the rest); static methods and free functions are module procedures; every procedure is
  `recursive`.
- Names: Fortran identifiers are case-insensitive and at most 63 characters. Mangle every name to a unique
  lower-case identifier (77 C# names are longer than 63 characters; shorten with a stable hash suffix).

## Values

- int/long/short/sbyte → integer(4)/(8)/(2)/(1), wrapping (-fwrapv). Unsigned types are the same kinds holding
  the bit pattern; comparisons, division, remainder, right shift and conversions to real go through runtime
  helpers. double/float → real(8)/real(4). bool → logical.
- Fortran's `.and.` and `.or.` may evaluate both operands (lessons 04 of the SWMM5 ports): C#'s `&&` and `||`
  become nested IFs (through temporaries in expression context).
- Integer division truncates toward zero and `mod` takes the dividend's sign, as in C#.
- Strings: C# string literals become character constants handed to the runtime (`R.Lit`).

## ref, generics, closures, exceptions

- `ref T` is a Fortran dummy argument (`intent(inout)`): pass the variable, element or component itself. A ref
  local or ref return is a Fortran pointer (`=>`); its target must be a pointer array element, a component of an
  object held by pointer, or a variable with the TARGET attribute.
- Generic runtime containers: specialised modules for primitive elements (vec_d, vec_i, vec_l, vec_b, vec_z,
  vec_f, as Java's VecD...), and one class(*)-based version for objects, with typed accessors the translator
  generates per element type (`select type`). Element makers as the Java translator passes them.
- Lambdas: each becomes a derived type extending an abstract delegate type (one per delegate signature) with a
  deferred `invoke`; captured variables become pointer components to cells (a captured local that is assigned
  lives in an allocated cell for its whole life).
- Exceptions: a pending-exception pointer in the runtime. A throw sets it and returns; after every call that can
  throw (a call-graph analysis over the engine and the runtime's throwing members), the caller tests it and
  returns or jumps to its handler. try/catch/finally become labels and GOTOs; a catch tests the pending object's
  type with `select type`.
- goto: Fortran has GOTO.

## Memory

The engine never deallocates an object (the translator cannot know when a reference is the last one, which the C#
leaves to .NET's collector). The program is linked against the system's Boehm collector instead (libgc1;
f90/gc/gc_wrap.c and the link step of f90/build.sh wrap malloc, calloc, realloc and free), which reclaims what is
unreachable. Without it the long models run out of memory (lessons/15).
